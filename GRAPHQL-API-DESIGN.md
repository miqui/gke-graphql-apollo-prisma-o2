# GraphQL API Design: Query Depth and Complexity Limits

A design note on the first finding of the GraphQL API best-practices review: **neither service
limits how deep or how expensive a query can be, and the schema is full of cycles.** Neither
`message-service` nor `issue-service` currently sets `validationRules`, `maxRecursiveSelections`,
or any other guard — see `new ApolloServer({...})` in `src/index.ts` and
`issue-service/src/index.ts`.

> **Status: implemented** in both services as `src/guards.ts` (`issue-service/src/guards.ts` for
> the other), wired in `index.ts`. The limits and guard code were first prototyped against the real
> `issue-service` schema and exercised through a real `ApolloServer` (`executeOperation`) with stub
> resolvers, and every query in [EXAMPLES.md](EXAMPLES.md) was run through it. The numbers in
> [Calibration](#calibration) are from that run. The structural work in
> [layer 4](#4-structural-fixes-that-make-layers-23-tighter-separate-work) is not done yet.

## The problem

GraphQL lets the client choose the shape of the query, and this schema lets it choose a shape that
never ends. Every one of these pairs is a two-way edge, so a query can ping-pong across it as many
times as it likes:

| Cycle | Fields |
| --- | --- |
| Workspace ↔ Project | `Workspace.projects` ↔ `Project.workspace` |
| Project ↔ Issue | `Project.issues` ↔ `Issue.project` |
| Issue ↔ Label | `Issue.labels` ↔ `Label.issues` |
| Issue ↔ Comment | `Issue.comments` ↔ `Comment.issue` |
| Issue ↔ Incident | `Issue.incident` ↔ `Incident.issue` |
| Issue ↔ Problem | `Issue.problem` ↔ `Problem.issue` |
| Issue ↔ Change | `Issue.change` ↔ `Change.issue` |
| Issue ↔ ServiceRequest | `Issue.serviceRequest` ↔ `ServiceRequest.issue` |
| Incident ↔ Problem | `Incident.problem` ↔ `Problem.incidents` |
| Problem ↔ Change | `Problem.changes` ↔ `Change.problem` |
| Comment → Comment | `Comment.replies` / `Comment.parent` (self-reference, unbounded thread depth) |

`message-service` has one: `Author.messages` ↔ `Message.author`.

(The table was generated by walking the object-type graph of `issue-service/src/schema.ts`,
treating `XConnection → XEdge → X` as a single hop.)

### Why it matters here specifically

Nearly every field resolver in `issue-service/src/resolvers.ts` issues its own Prisma query per
parent (`Issue.project`, `Issue.labels`, `Issue.incident`, `Comment.replies`, …), so **resolver
calls ≈ database queries**. Cycles plus per-parent queries means a small request text can turn into
a very large number of round trips.

This 164-byte query is only nine fields deep:

```graphql
{ workspace(id: "w") { projects { issues(first: 10) { edges { node {
    id
    project { workspace { projects { id } } }
    comments { replies { replies { id } } }
} } } } } }
```

Run against stub resolvers that return 10 items per list, it triggers **11,411 database-bound
resolver calls** (`Comment.replies` alone is 11,000 of them). Real tables will usually have fewer
rows per level, so treat that as a worst case at 10 rows per list — but the shape is the point: cost
grows multiplicatively with every level the client adds, and the client controls the levels.

Two things this query shows about the fix:

- **A depth limit alone would not stop it.** Depth 9 passes the depth limit of 10 proposed below,
  and lowering it much further would start rejecting legitimate queries (the deepest one in
  `EXAMPLES.md` is 7). It is cost, not depth, that is abusive here.
- **A cost limit alone is not enough either.** Depth guards are cheap, exact, and need no
  per-field tuning; they catch the ping-pong and fragment-nesting cases before any cost analysis
  runs.

### What Apollo Server already gives us

Checked against `@apollo/server` 5.5.1 in `node_modules`:

| Protection | Default | Notes |
| --- | --- | --- |
| Batched HTTP requests (`allowBatchedHttpRequests`) | off | Good — one operation per request. Keep it off, otherwise an array body multiplies whatever limit we set. |
| CSRF prevention (`csrfPrevention`) | on | Unrelated to cost, but already handled. |
| `maxRecursiveSelections` | **off** | Caps the number of selections *after fragment expansion* (`true` = 10,000,000). Stops fragment-explosion documents. Not a depth or cost limit. |
| Depth limit | **none** | |
| Complexity / cost limit | **none** | |
| Request body size | `express.json()` default (100kb) | Bounds document size only, not what the document costs to execute. |

## Design

Four layers, cheapest first. Each catches something the others miss.

### 1. `maxRecursiveSelections: true` (built in)

One line in the `ApolloServer` config. Rejects documents whose fragment expansion is enormous
before anything else looks at them. When it is enabled, Apollo runs any custom `validationRules`
after it, which is the order we want.

### 2. Depth limit — `MAX_DEPTH = 10`

Depth is the number of nested **fields** below the operation root, following fragment spreads and
inline fragments. `__typename` and introspection fields are free, so Apollo Sandbox keeps working
(a plain introspection query is deeper than 10).

Why 10: the deepest query in `EXAMPLES.md` is 7 (`workspace → projects → issues → edges → node →
labels → name`). A Relay connection costs two levels (`edges`, `node`) by itself, so 10 leaves
three levels of headroom over the deepest current example, while rejecting the ping-pong and
fragment-hidden cases outright (depth 18 and 12 in the [tests](#calibration)).

The depth walk **must** follow fragments. A visitor that only counts `Field` nodes in the operation
body is bypassed by putting the nesting inside `fragment` definitions.

### 3. Complexity limit — `MAX_COMPLEXITY = 5000`

Cost is computed per operation with [`graphql-query-complexity`](https://github.com/slicknode/graphql-query-complexity)
(2.0.0, peer `graphql ^16.6 || ^17`; this repo has `graphql` 16.14.2) and a custom estimator:

```
cost(field) = 1 + cost(children) × multiplier

multiplier =
  clamped `first`  (1–100, default 20)   for a connection field (any field with a `first` argument)
  1                                      for `edges` on a *Connection (the parent's `first` already bounds it)
  10                                     for any other list field — a placeholder for "unbounded"
  1                                      for everything else
```

Three properties of this model worth calling out:

- **Aliases are priced.** `a1: issue(...) a2: issue(...) … a100: issue(...)` costs the sum, so the
  alias-multiplication trick is not a way around the limit (100 aliases of a modest query price at
  30,300).
- **`first` is clamped the same way the resolver clamps it** (`clampFirst` in
  `issue-service/src/resolvers.ts`), so a client asking for `first: 100000` is priced as 100, which
  is what it will actually get.
- **The "10 for unbounded lists" multiplier is a stopgap.** `Workspace.projects`,
  `Project.labels`, `Issue.labels`, `Issue.comments`, `Comment.replies`, `Label.issues`,
  `Problem.incidents`, `Problem.changes` and `issuesByLabel` have no `first` argument or `take`
  today, so the estimator has to guess. Once those are paginated or capped (layer 4), replace the
  guess with real bounds and the cost numbers get tighter.

#### Why a plugin, not a validation rule

`graphql-query-complexity` also ships `createComplexityRule()`, and the depth check could be a
`validationRules` entry too. We deliberately do both checks in one Apollo **plugin**
(`didResolveOperation`) instead, for two reasons found while prototyping:

1. **Variables.** Validation runs before variables are coerced. The library's README says as much:
   `createComplexityRule` takes a static `variables` option "because the variables are not
   available in the visitor", which is no help for per-request variables. A client sending `issues(first: $n)` with
   `{"n": 100}` would be priced at the default page size (20) — a 5× under-count that the client
   controls. `didResolveOperation` has `request.variables`. Verified: with the plugin,
   `first=$n` prices 38 for `n=5`, 703 for `n=100`, 703 for `n=100000` (clamped), and 143 when `n`
   is omitted (default 20).
2. **Stable error codes.** Apollo relabels validation-rule errors as `GRAPHQL_VALIDATION_FAILED`
   (observed: a custom `QUERY_TOO_DEEP` code came back as that). Errors thrown from a plugin keep
   theirs, so clients and dashboards can tell `QUERY_TOO_DEEP` and `QUERY_TOO_COMPLEX` apart
   from an ordinary invalid query. Both come back as **HTTP 400**.

The existing `metricsPlugin` reads `extensions.code` off every error in `willSendResponse`, so
`graphql_errors_total{error_code="QUERY_TOO_DEEP" | "QUERY_TOO_COMPLEX"}` shows up with no telemetry
changes. List `metricsPlugin` first in `plugins` so it is registered before the limits plugin.

### 4. Structural fixes that make layers 2–3 tighter (separate work)

Limits are a backstop. The reason the numbers above are so large is the schema and resolvers, and
those should be fixed regardless:

- **Cap or paginate every unbounded list field** (listed above). This also lets the cost estimator
  drop its guess.
- **Batch per-parent lookups with per-request DataLoaders** (created in an Apollo `context`
  function) so `Issue.project` for 100 issues is one query, not 100. This turns the 11,411-call
  worst case into a handful of queries per level.
- **Bound `Comment.replies` nesting** (or flatten threads) — it is the one true self-cycle and the
  biggest single contributor above.

## Proposed implementation

New file, one per service (`src/guards.ts` and `issue-service/src/guards.ts`), plus
`npm install graphql-query-complexity@^2.0.0` in each. It type-checks under this repo's
`tsconfig` settings (`strict`, `module`/`moduleResolution: node16`).

```ts
import type { ApolloServerPlugin } from "@apollo/server";
import { GraphQLError, Kind } from "graphql";
import type { DocumentNode, FragmentDefinitionNode, SelectionSetNode } from "graphql";
import { fieldExtensionsEstimator, getComplexity } from "graphql-query-complexity";
import type { ComplexityEstimator } from "graphql-query-complexity";

export const MAX_DEPTH = 10;
export const MAX_COMPLEXITY = 5000;
const DEFAULT_PAGE_SIZE = 20;
const MAX_PAGE_SIZE = 100;
const UNBOUNDED_LIST_ESTIMATE = 10;

// Field-nesting depth of the operation, following fragment spreads. __typename and
// introspection fields are free so the Sandbox keeps working.
function operationDepth(
  selectionSet: SelectionSetNode,
  fragments: Map<string, FragmentDefinitionNode>,
  memo = new Map<string, number>(),
  visiting = new Set<string>(),
): number {
  let deepest = 0;
  for (const selection of selectionSet.selections) {
    if (selection.kind === Kind.FIELD) {
      if (selection.name.value.startsWith("__")) continue;
      const below = selection.selectionSet
        ? operationDepth(selection.selectionSet, fragments, memo, visiting)
        : 0;
      deepest = Math.max(deepest, 1 + below);
    } else if (selection.kind === Kind.INLINE_FRAGMENT) {
      deepest = Math.max(deepest, operationDepth(selection.selectionSet, fragments, memo, visiting));
    } else {
      const name = selection.name.value;
      const fragment = fragments.get(name);
      if (!fragment || visiting.has(name)) continue; // cycles are rejected by graphql-js's own rules
      if (!memo.has(name)) {
        visiting.add(name);
        memo.set(name, operationDepth(fragment.selectionSet, fragments, memo, visiting));
        visiting.delete(name);
      }
      deepest = Math.max(deepest, memo.get(name) ?? 0);
    }
  }
  return deepest;
}

function fragmentsOf(document: DocumentNode): Map<string, FragmentDefinitionNode> {
  const fragments = new Map<string, FragmentDefinitionNode>();
  for (const definition of document.definitions) {
    if (definition.kind === Kind.FRAGMENT_DEFINITION) fragments.set(definition.name.value, definition);
  }
  return fragments;
}

// cost(field) = 1 + cost(children) * multiplier
//   connection field (has a `first` arg): clamped `first`, or the default page size
//   `edges` on a *Connection:             1 (the parent's `first` already bounds it)
//   any other list field:                 UNBOUNDED_LIST_ESTIMATE (drop once the list is capped)
//   everything else:                      1
const costEstimator: ComplexityEstimator = ({ type, field, args, childComplexity }) => {
  if (field.name === "edges" && type.name.endsWith("Connection")) return 1 + childComplexity;
  let multiplier = 1;
  if (field.args.some((arg) => arg.name === "first")) {
    multiplier = Math.min(Math.max(Number(args.first ?? DEFAULT_PAGE_SIZE), 1), MAX_PAGE_SIZE);
  } else if (String(field.type).includes("[")) {
    multiplier = UNBOUNDED_LIST_ESTIMATE;
  }
  return 1 + childComplexity * multiplier;
};

function reject(message: string, code: "QUERY_TOO_DEEP" | "QUERY_TOO_COMPLEX"): never {
  throw new GraphQLError(message, { extensions: { code, http: { status: 400 } } });
}

// A plugin rather than validationRules: validation runs before variables are coerced, so
// `first: $n` would be priced at the default page size; didResolveOperation has them.
export const queryLimitsPlugin: ApolloServerPlugin = {
  async requestDidStart() {
    return {
      async didResolveOperation({ request, document, operation, schema }) {
        if (!operation) return;
        const depth = operationDepth(operation.selectionSet, fragmentsOf(document));
        if (depth > MAX_DEPTH) reject(`Query depth ${depth} exceeds the maximum of ${MAX_DEPTH}.`, "QUERY_TOO_DEEP");

        const complexity = getComplexity({
          schema,
          query: document,
          variables: request.variables,
          operationName: request.operationName,
          estimators: [fieldExtensionsEstimator(), costEstimator],
        });
        if (complexity > MAX_COMPLEXITY) {
          reject(`Query complexity ${complexity} exceeds the maximum of ${MAX_COMPLEXITY}.`, "QUERY_TOO_COMPLEX");
        }
      },
    };
  },
};
```

Wiring, in each service's `src/index.ts` (`introspectionEnabled` comes from `src/http-config.ts`,
which reads `GRAPHQL_INTROSPECTION`):

```ts
import { queryLimitsPlugin } from "./guards";

const apollo = new ApolloServer({
  typeDefs,
  resolvers,
  plugins: [
    metricsPlugin,
    queryLimitsPlugin,
    introspectionEnabled
      ? ApolloServerPluginLandingPageLocalDefault({ embed: true })
      : ApolloServerPluginLandingPageDisabled(),
  ],
  includeStacktraceInErrorResponses: false,
  introspection: introspectionEnabled,
  maxRecursiveSelections: true,
});
```

What a rejected client sees:

```json
{
  "errors": [{
    "message": "Query complexity 112712 exceeds the maximum of 5000.",
    "extensions": { "code": "QUERY_TOO_COMPLEX" }
  }]
}
```

with HTTP status 400.

### `message-service` prices `limit`, not `first`

The estimator above prices connections from a `first` argument, which is what `issue-service` uses.
`message-service`'s `messages(limit:, offset:)` uses `limit`, so its `src/guards.ts` differs in
exactly one place: it clamps `limit` (default 50, max 200, same as `clampPagination` in
`src/resolvers.ts`) and treats `items` on a `*Page` as bounded by the parent. If `message-service`
later moves to Relay connections, the two copies can converge. Its `authors` and `Author.messages`
lists are unbounded today and priced with the "×10" placeholder, like the issue-service ones.

## Calibration

Every ```` ```graphql ```` block in [EXAMPLES.md](EXAMPLES.md) (25 of them) was run through a real
`ApolloServer` with `maxRecursiveSelections: true` and the plugin above. **None is rejected by the
limits.** The heaviest ones (numbers are `EXAMPLES.md`'s own section numbers):

| Query | Depth | Complexity |
| --- | --- | --- |
| issue-service #9 — workspace → projects → issues(first: 10) → labels | 7 | 3,022 |
| issue-service #15 — workspace → projects → issues(kind: INCIDENT, first: 10) → incident | 7 | 1,112 |
| issue-service #8 — workspace → projects → issues(first: 5) | 6 | 462 |
| issue-service #16 — incidents(first: 20) → issue → project | 6 | 281 |
| message-service (all) | ≤ 4 | ≤ 43 |

(Complexity for #9 and #15 is dominated by the "×10 for unbounded lists" placeholder on
`Workspace.projects` and `labels`; it will fall once those lists are bounded.)

Probes:

| Query | Result |
| --- | --- |
| `issue → project → issues(first: $n)` with `n = 100`, 5 scalar fields | ok (703) |
| Same with `n = 100000` | ok — clamped, priced as 100 (703) |
| The 164-byte fan-out above (depth 9) | **rejected `QUERY_TOO_COMPLEX`** (112,712) |
| `project → issues → node → …` repeated 4× (ping-pong) | **rejected `QUERY_TOO_DEEP`** (depth 18) |
| Nesting hidden inside `fragment` definitions | **rejected `QUERY_TOO_DEEP`** (depth 12) |
| 100 aliases of `issue { project { issues(first: 100) … } }` | **rejected `QUERY_TOO_COMPLEX`** (30,300) |
| Introspection query (Sandbox) | ok — introspection fields are exempt from depth |
| `{ issue(id: "1") { id title } }` | ok (3) |

A worst-case *legitimate* page — `workspace → projects → issues(first: 100)` with five fields per
issue — prices at 7,012 and would be rejected. That is the trade-off the `first` clamp and the
"×10 unbounded" guess produce today; it is a signal to fetch per-project, and it will loosen when
`Workspace.projects` gets a real bound. If it turns out to bite real clients, raise
`MAX_COMPLEXITY` deliberately rather than removing the guard.

## Rollout

1. **Add `src/guards.ts` and the wiring to both services** with the limits above. Because the
   error codes flow into `graphql_errors_total{error_code=…}`, any legitimate client that trips a
   limit is immediately visible in Grafana.
2. **If you would rather observe first**, log the computed depth and complexity instead of
   rejecting (drop the two `reject` calls, log instead) for a period, look at the distribution of
   real traffic, then set the maxima from it.
3. **Then the structural work** in layer 4, and lower `MAX_COMPLEXITY` / drop the "×10" placeholder
   as lists get real bounds.
4. Add a small test for `operationDepth` and the estimator. The repo has no test runner today, so
   this is a good first reason to add one.

Adjacent hardening that is out of scope here but complements it: per-client rate limiting at the
ingress (`k8s/ingress.yaml`, `k8s/issue-service-ingress.yaml`; neither sets any `limit-*`
annotation today), and authentication, which neither service has. (Introspection is now opt-in
outside local dev and CORS is an explicit allowlist; see `src/http-config.ts`.)

## Alternatives considered

| Option | Verdict |
| --- | --- |
| `graphql-depth-limit` | Depth only, and the package's last release was May 2022. The ~30-line function above does the same job and is fragment-safe. |
| `createComplexityRule()` / `validationRules` for both checks | Simpler wiring, but cannot see variables and loses the custom error code (see [Why a plugin](#why-a-plugin-not-a-validation-rule)). |
| A bundled hardening library (e.g. `@escape.tech/graphql-armor`) | Not evaluated in detail. A reasonable alternative if you prefer one dependency covering depth, cost and alias limits over ~90 lines of local code. |
| Persisted queries / operation allowlist | The strongest option — clients can only run pre-approved operations, so cost is known ahead of time. It adds a build/registration step to every client change, which is heavy for a disposable dev cluster. Worth revisiting if the API is ever exposed to third parties. |
| Execution timeouts | A useful last resort but reactive: the work is already running. Complements, does not replace, static limits. |
